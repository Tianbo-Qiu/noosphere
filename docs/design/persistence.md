# Persistence layer

`internal/db` is the only Go package that talks to Postgres. The rest of the code calls its functions with Go values and gets Go values and Go errors back, never SQL or Postgres error codes.

## Generated and hand-written code

The package mixes two kinds of code:

- **Generated by sqlc**: one Go function per query in `db/queries` (such as `CreateIdentity`), a struct per table, and the `Queries` type that runs them. These files start with `Code generated by sqlc. DO NOT EDIT.` and are rebuilt with `make generate`.
- **Hand-written**: the Go types that columns map to (`types.go`), error handling (`errors.go`), and operations that need several queries in one transaction, such as sign-up (`signup.go`).

## Typed values

Callers work with Go types, not raw database values. `Traits` is the identity's profile stored in a `jsonb` column, `CredentialType` is the kind of credential (`CredentialTypePassword`), and `PasswordConfig` is a password credential's stored config. Turning a struct into JSON for a `jsonb` column happens inside `internal/db`, so callers never build JSON by hand.

## Connections

The server opens one [pgx](https://github.com/jackc/pgx) connection pool at startup and pings the database once, because the pool only connects when it is first used and a wrong address should stop the server immediately rather than fail the first request.

The generated `Queries` runs on anything that can execute SQL: the pool, a single connection or a transaction. The same query functions are used inside and outside transactions.

## Transactions

An operation that writes several rows runs in one transaction, so it either completes or leaves nothing behind. Sign-up inserts an identity, its credential and the credential's identifier; if the identifier is taken, the identity and credential are rolled back too.

These functions accept anything with a `Begin` method. The server passes the pool, which starts a transaction. Tests pass their own transaction, on which `Begin` starts a savepoint, so the operation commits or rolls back inside the test's transaction and the test can still roll everything back at the end.

## Input at the boundary

Values that must follow a rule before they are stored are fixed or rejected here, before the transaction starts. Login identifiers are normalized with [PRECIS](../standards/precis.md); an identifier that cannot be normalized returns `ErrInvalidIdentifier`.

## Errors

When Postgres rejects a write, `internal/db` checks the error code and the name of the constraint that fired, and returns a plain Go error:

| Postgres reports | Caller receives |
|---|---|
| unique violation on `(type, identifier)` | `ErrIdentifierTaken` |
| identifier fails normalization (before any SQL runs) | `ErrInvalidIdentifier` |

Callers test with `errors.Is`. The original cause stays wrapped inside, so logs still show what happened. Checking the constraint name matters: a table can have several unique constraints, and only one of them means "this email is already registered".

## No repository interface

Callers use the package's functions directly; there is no interface in front of them and no in-memory fake. The behavior worth testing here, such as constraints, transactions and error mapping, only exists in a real database, so tests run against Postgres (see [Testing](testing.md)).
